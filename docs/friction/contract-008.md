# contract-008: readings taken for A34 and A37 under dora 0.5.0 (lanes cpp, core, dora; 2026-11-16)

Lanes cpp, core and dora implemented §15 A31-A34, A36 and A37 on `build/v0` with no change to `docs/CONTRACT.md`, `kpi/` or the public surface. One amendment cannot be built as written (§1) and one is silent where A37 needs a choice (§2); these are the readings taken. The dispatcher should ratify or amend them.

1. **A34's "exits with a code dora does not restart" (§9.2, §15 A34, consumer-017).** dora 0.5.0 restarts a node with `restart_policy: always` whatever its exit code (`binaries/daemon/src/spawn/prepared.rs`, `restart_loop`: `RestartPolicy::Always => true`). Only `on-failure` spares exit 0, and `kpi/churn/test_churn.py` pins `always` on every node (§9.2). So no exit code is final under the emitted dataflow.
   - **Reading:** a final refusal does not exit until the dataflow stops. The host marks it (`failed`, then `refused` for activate), keeps its process (no data frame sent, no restart possible), and exits non-zero only after dora's Stop, which disables restarts (`disable_restart` on a stop). The launcher raises on either marker, naming the refusal, and stops the dataflow, in real time and lockstep alike. Both hosts do this for every final refusal on their main thread: activate, `lk_create`, `dlopen` and missing symbols in `lk-dora-host`; activate and "cannot build its components" in the Python host. A skewed peer (exit 3, found on the RX thread) and the init watchdog (exit 4) still exit at once, as T11 judges them.
   - **Consequence:** a refused node outlives its refusal until someone stops the dataflow. `Deployment.start()` always does, at once; a dataflow started some other way keeps an idle refused node rather than a restart loop.
   - **Amend if wanted:** A34's "exits with a code dora does not restart" reads "exits only after dora's Stop (restart_policy `always` restarts any exit)". The other route, `restart_policy: on-failure` with exit 0 on a refusal, contradicts §5.7's "exits non-zero" and the churn test.

2. **Which nodes a real-time `stop()` signals first, once A37 adds the Python hosts (§9.2, §15 A30, A37).** A30 signals the native nodes first and then runs `dora stop`. Signalling every Python host as well would stop the readers together with the node whose last words they must read, and A37's own test would fail: a reader stopped before the box's final frames arrive never steps on them.
   - **Reading:** `stop()` signals, in waves, every local node whose outputs another *component's* node reads, upstream first; in a cycle (the reference cell's arm and planner read each other) its native nodes first, as A30 did. It waits for each wave's `drained` marker (10 s in all), then runs `dora stop`. Nodes only the gateway reads (readers, sinks: the gateway takes every node's health and metrics for `lk top`) and the gateway get dora's Stop, which dora delivers after every frame sent before it, so a signalled node's final drain reaches them and the recording.
   - **What it does not promise:** between two signalled waves (a chain of three Python processes, or the planner after the arm) a later wave is signalled about 50 ms after the earlier one drained, so a frame still in the daemon can arrive after its reader stopped. Only dora's own Stop is ordered after frames. Nothing in v0 needs a middle node's final words; a reader of them sits at the end, where it gets dora's Stop.
   - A signalled node waits for dora's Stop for at most 15 s (`lk-dora-host` and the Python host alike), longer than the whole drain, so dora never restarts it mid-stop.
   - **Amend if wanted:** A30's "a dora stop() signals native nodes first" reads "signals the nodes other components read, upstream first (in a cycle, native nodes first)".
